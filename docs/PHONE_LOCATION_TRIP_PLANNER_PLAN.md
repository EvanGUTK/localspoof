## Phone location: one dot, honest provenance

Add a service-owned framework location reader, distinct from the mock writer. Start it only after a visible phone action has enabled the foreground service and granted precise location permission; desktop requests must not start a hidden service or grant permissions. The approved USB controller may receive one latest location value through authenticated Snapshot. Public Hello, pairing and rejection responses never expose it.

Before provider overrides are armed, obtain framework GPS/network updates and retain only the latest valid non-mock reading in RAM. Reuse the existing foreground service and permissions; no GMS dependency, Internet permission, history, file cache or background-location permission is required for this scope. Prefer a single API-29-compatible named-provider listener registration approach and explicitly remove updates on teardown. An optional one-shot refresh can use API 30 `getCurrentLocation` with cancellation, with an API 29 listener fallback; it must not block heartbeat dispatch. Android documents these versions, permissions and cancellation behavior in [LocationManager](https://developer.android.com/reference/android/location/LocationManager).

Filter mocked framework readings with `isMock` on API 31+ and `isFromMockProvider` on API 29/30. Use `elapsedRealtimeNanos` against the phone's monotonic clock to reject stale, future and out-of-order fixes. Coordinate/accuracy values must be finite and within explicit bounds. These APIs and their mock/freshness meanings are documented in [Android Location](https://developer.android.com/reference/android/location/Location). Agreed freshness is at most 30 seconds for both DEVICE and SIMULATION; supplied accuracy must be positive and at most 10 km. Missing accuracy is omitted and poor precision is visibly identified rather than implying GPS-level certainty. Phone, UI and fixtures use those same bounds. A non-mock flag is platform provenance, not proof against a compromised device.

Detach/cancel the real reader before `FrameworkLocationProvider.prepare()` replaces GPS/network with test providers. The current adapter replaces both providers, so a fresh actual position during mocking is not promised. While armed, publish the latest successfully injected sample with source SIMULATION; do not use an unsubmitted planned target or READY origin as a claimed phone reading. Hold/Pause continue to expose the last successfully refreshed simulation. An injection failure must not advance the dot to an unsubmitted destination. Clear the previous DEVICE sample on the transition so it cannot remain visible as a supposedly current actual position while mocking.

Proposed authenticated `payload.phoneLocation` is either null or `{point:{lat,lon},source:DEVICE|SIMULATION,accuracyMeters,ageMs}`. Phone computes age from its monotonic clock; desktop adds time elapsed since receipt rather than comparing phone/Windows boot clocks. Describe DEVICE as a phone reading and SIMULATION as the app's submitted simulated position; this is not a guarantee of what Life360 or every receiving app reports. Expose simple status for permission denied, locating, unavailable, stale or disconnected. Never substitute Chicago demo points, IP geolocation or an old last-known reading as current.

Ownership follows the visible service/provider generation; remote access additionally requires the approved channel. Stop, detach, failure and process death clear the reading and remove listeners; stale/invalid readings become unavailable and late callbacks cannot repopulate a successor. If USB disconnect leaves ordinary playback running, its local simulated sample may remain available to that phone session, but desktop immediately discards its received point and cannot read again without approval. Pre-mock acquisition can serve phone-local status while the explicitly enabled foreground service remains active; it does not imply remote sharing before approval. Android's app may display local status without disclosing data through public protocol replies.

## Drive/Fly stages and editable options

Keep Instant/Walk available as secondary existing modes; Drive/Fly become the main trip choices. Drive reuses the exact road-route validation, atomic Prepare/Commit, explicit phone Start and canonical m/s engine.

Fly stages are: departure ground travel/acknowledged instant departure placement → boarding → observed airplane mode on → timed or jumped flight interval → acknowledged arrival placement → settling → restoration of session-owned connectivity → final ground travel/acknowledged instant destination placement → destination hold. Defaults are DRIVE/DRIVE/TIMED. The default departure/arrival are nearest eligible catalog airports to the frozen origin/destination. If a required driving leg lacks valid road access, explain the failure and offer another sorted candidate; bound any automatic fallback rather than unbounded provider probing. User can override either airport by searching the full bundled catalog. “Destination airport” means an eligible airport near the selected destination; do not claim actual airline service between chosen airports.

Expose departure/arrival **Drive** or **Instant**, flight duration, boarding/settling durations within supported bounds, and **Timed flight** or **Jump flight wait**. Root explicitly authorized both instant ground options. An INSTANT leg is typed as such, never forged road geometry; departure targets the selected catalog airport point, arrival starts at its catalog airport point and targets the final destination. DRIVE endpoints use validated actual road access within 5 km. A mixed flight therefore connects the applicable catalog/road-access endpoints. No new airport-access network API is needed; both-INSTANT preview makes no road-route requests.

All FLIGHT requests use `routeSource:FLIGHT_JOURNEY`. Ordered preview `segments` have `{role:DEPARTURE|AIR|ARRIVAL,kind:DRIVE|INSTANT|FLIGHT,points,durationMs,routeSource,routeProvider?}`. DRIVE has its actual ONLINE_ROUTER/OFFLINE_GEOPACK source, INSTANT has INSTANT_LOCATION, and AIR has FLIGHT_JOURNEY; instant/jumped durations are zero. Render each kind distinctly. The air connection/instant connector must not appear as a drivable route, traffic prediction or actual airline track. Root requested engine-side great-circle interpolation for TIMED air travel, including antimeridian handling; the dot follows successfully submitted samples rather than a UI-only animation. Preserve actual airport access endpoints for DRIVE, catalog coordinates for INSTANT, and disclose that distinction. Invalid required legs prevent staging the whole journey.

Changing any draft timing, speed, address, airport or leg mode invalidates the prepared ID and requires a fresh preview/commit. Active editing builds a new candidate without silently replacing the running session. A planned flight jump bypasses waiting only, then advances through arrival placement acknowledgment, settling and restoration. It cannot jump over ground travel, airplane-on observation or failed placement. No live phase-jump command is added in 0.5; jump is an explicit prepared-plan option. Pause and Stop retain their existing authority.

MANUAL is the guided phone-radio path. USB automation remains an authenticated phase-specific native capability from the committed plan; there is no arbitrary shell command or newly privileged APK radio toggle. Jumping still checks observed airplane state for real radio policies, submits the arrival mock before restoration, restores only the session's own change and respects phone overrides/Stop. SIMULATION remains an explicitly chosen policy that does not change radio settings; it must never be substituted silently after automation failure.
