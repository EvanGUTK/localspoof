# USB approval pairing: plan and independent review

Status: final saved source review and 0.4 build/signing/package checks pass; signed 0.4 phone installation and bounded real approval interaction passed; journey/radio and sustained reliability remain unqualified. This change is authorized by the user's request for reliable pairing without typing, rather than a longer timer. ECC security-review is applied to the ephemeral credential and connection boundary.

## Confirmed failure and intended interaction

The current `SimulationService.ENABLE_DESKTOP` action unconditionally closes its `PhoneControlServer`, then `RuntimeModel.enableDesktop()` increments the controller generation. Asking for a fresh displayed secret therefore closes the connection on which Windows is trying to pair. The previous idle-frame fix addresses a separate failure; it does not fix this refresh action.

Enable USB control once on the phone. Select the validated physical phone on Windows and request pairing. Both screens display the same six-digit comparison number. The person checks that number and explicitly approves that particular request on the phone, or rejects it. There is no typed secret, clipboard, account, remembered computer identity, or automatic approval. Repeated Enable while the listener is already enabled preserves its socket, controller generation, pending request and approved lease.

## Proposed minor-version 2 contract

Windows native code generates a fresh 128-bit client nonce for a new pairing attempt; it never accepts a nonce chosen by the renderer. The phone generates a fresh random 128-bit pairing ID and an internal accepted-socket channel ID. All wire nonce/ID strings use exactly 32 lowercase hexadecimal characters. Random generation uses the platform secure random source; see [Android SecureRandom](https://developer.android.com/reference/java/security/SecureRandom).

The comparison number is the first four SHA-256 digest bytes of the exact UTF-8 string `localspoof-pair-v2:<clientNonce>:<pairingId>`, interpreted as unsigned big-endian, modulo 1,000,000, padded with leading zeroes to six digits. The desktop computes it independently; it must reject any inconsistent phone-reported value rather than display an unverified string. This exact byte contract requires shared synthetic vectors, including leading-zero and unsigned-high-bit cases. Android exposes SHA-256 through [MessageDigest](https://developer.android.com/reference/java/security/MessageDigest).

Independently calculated vectors use nonce `00000000000000000000000000000000`:

| Pairing ID | First four digest bytes | Comparison number |
|---|---|---|
| `11111111111111111111111111111111` | `0108621e` | `326622` |
| `ffffffffffffffffffffffffffffffff` | `a863449c` | `077916` |
| `00000000000000000000000000000004` | `d0245fad` | `044717` |

`PairRequest` carries the native nonce. Its successful response carries the pending pairing ID and comparison number. Repeating the same request on its accepted channel returns the same pending identity/number without extending expiry. A different nonce or channel cannot replace a pending request or approved controller. `PollPair` requires the owning channel, nonce and pairing ID. Until phone approval, public responses contain no token or session identity. After explicit approval, only the owning PollPair receives the rotated random token and session identity; native code consumes those fields before returning renderer-safe state.

Phone approval/rejection carries the displayed pairing ID back to the coordinator and succeeds only if it still identifies the current pending request. A stale callback must never approve or reject a later request. Authorization, token matching, cached-response access, resource upload, and asynchronous planning completion all additionally verify the internal accepted channel. A token copied to another socket must not authorize operations or disclose an authenticated response.

The comparison number is a human check, not a credential. This is an approval mechanism inside the existing authorized-ADB/validated-physical-USB boundary, not an authenticated key exchange or protection against a compromised computer, phone, or already authorized ADB application. In particular, an attacker who can rewrite transport messages can search replacement public IDs offline for the same six-digit number; no commitment or authenticated encryption prevents that attack here. An observer of an approved transport remains outside this design's protection. No undetectability or encryption claim follows from displaying six digits.

## Deadlines, cancellation and reconnect

The existing fixed 120-second preauthentication bound, five-second absolute partially arriving frame deadline and six-second approved heartbeat lease remain. Public Hello, PollPair, idempotent requests and comparison-number display do not renew authority. An approved or revoked connection cannot fall back into its old preauthentication window. Stop synchronously revokes control and closes the socket; ordinary USB loss retains the established phone playback behavior.

The saved lease implementation separates opt-in from attempt lifetime. Explicit phone Enable retains a listener opt-in until Stop/disable; it does not grant authority. Each accepted channel still has its fixed 120-second preauthentication window, and a pending request also expires after a fixed 120 seconds without renewal; the earlier applicable bound wins. Repeating Enable or the same request does not renew either bound. Rejection, expiry or owner disconnect retires that channel's request, while a freshly accepted channel can make a new deliberate request while the listener remains enabled. This avoids both an indefinitely renewable attempt and an enabled UI that can never accept a retry.

Windows retry closes only its own connection/forward, revalidates the same selected physical USB device and establishes a new native nonce. It does not replace another approved controller or retry indefinitely. After approval, rejection, revocation, loss or expiry, renewed control needs a new deliberate request and fresh phone approval. Late results are guarded by the existing activity epoch and current connection ownership.

## Required checks and delivery boundaries

Deterministic Android/native tests must cover shared comparison vectors, leading zeroes, malformed/extra fields, wrong channel/nonce/ID, stale approval callback, duplicate request stability, conflicting request rejection, fixed expiry, token delivery only after approval, cross-socket token rejection, and Stop/revoke/disconnect cleanup. Check every authorization path, including cached acknowledgments and asynchronous plan/resource work, rather than only Heartbeat.

UI regressions must establish that no secret input or clipboard action remains, the number is displayed consistently, an old async completion cannot overwrite a newer connection, pending/declined/expired/retry states are actionable, and controls do not imply pairing before phone approval. Existing responsive layout and API 29 privacy checks remain relevant.

Rebuild the signed APK and Windows bundle together with matching protocol capabilities and trusted companion bytes. Reject incompatible earlier pairing versions with clear upgrade instructions; do not silently fall back to secret entry. Preserve the signing identity and perform the existing signing/trust gates.

Actual public-Hello checks establish connection readiness only. Real comparison/approval, rejection/retry, repeated Enable preserving a live channel and sustained approved heartbeats require separately recorded qualification. Do not collect private pairing tokens or bypass approval during verification. Hardware tests must distinguish this repair from residual cable/ADB transport, long native-handler, sleep and scheduling failures.
