# LocalSpoof 0.6 mobile rendering review

Independent source review of the mobile map and icon repair, 2026-10-03. **No blocking findings.** This review did not change the domain, MainActivity, playback authority, or Android device state.

The original immediate four-request admission limit rejected normal MapLibre tile/font bursts. The replacement `MobileMapGate` keeps four active requests and at most 32 waiting callers, with a separate 12-second queue deadline. A fair semaphore admits queued work; failed/closed/interrupted admission cannot release an unowned permit. Waiting callers observe closure at approximately 100 ms polling intervals. Every admitted `MobileMapNetwork.get` exits through connection removal/disconnection and permit release, including HTTP, encoding, byte-limit, cancellation and read failures. Existing response timeouts and byte limits remain. Active HTTP cancellation is best effort; queue and response deadlines are separate, so their times can add.

The map keeps the latest native state independently of style readiness. State revisions remain dirty when a style is not ready, and `idle` or `style.load` retries rendering. An unchanged revision does not endlessly reload sources or refit the camera. The packaged `bootstrap.js` shows a static failure message for startup/graphics/data failure, and later successful idle readiness clears it. Its status contains no position, route, search query or operational logging.

The WebView still serves only exact packaged asset paths and bounded fixed-provider requests. JavaScript module/bootstrap MIME types are correct. Default WebView network loads, file/content access, DOM storage, cookies and mixed content remain disabled; CSP remains restricted to the app origin and required local worker/image mechanisms. HTTPS failures are canceled rather than overridden. There is no JavaScript-to-native command bridge. Map selection continues through the narrowly validated app-origin coordinate navigation callback. The repair introduces no persisted location or credential, broader endpoint, or authorization change.

Settings, bookmark and search controls draw fixed geometry in a 24 dp Canvas within 48 dp targets, avoiding OEM font glyph substitution. The test uses measured Compose dimensions plus rasterization of the production drawing function under normal and enlarged font scale. This is meaningful pixel evidence for the icon geometry; it is not a hardware PixelCopy claim.

The reviewed `MobileMapPolicyTest` exercises queued burst admission, cancellation, fixed paths, origin/callback validation, WebView restrictions and fresh submitted-position state. Queue overflow/timeout branches were reviewed in source; the current burst test does not independently establish every scheduling interleaving. The latest root build log, `.build/global/v06-android-render-final.log`, reports debug/release assembly, unit tests and lint completing successfully. Broader release counts belong in the validation record.

Root's physical isolated WebView evidence is recorded in `.build/global/v06-map-physical-result.json`, using Android WebView 153.0.8010.36 and package `dev.localspoof.mapqa`, with public Chicago coordinates and no location permission. The old immediate gate rejected 22 of 32 high-zoom requests and rendered zero features. The queued/deferred-state case completed 48 of 48 requests, rendered 1,740 features at zoom 15, displayed markers and reported no map/console error. The production map assets were exercised with restrictive interception. This establishes the reported rendering repair in that isolated harness; it does not qualify the final companion's real-location acquisition, mock playback, background operation or airplane-mode handling.

Two small resilience improvements remain optional: recheck closure after registering a newly created HTTP connection to narrow the close/registration race, and record a revision as rendered only after all rendering work succeeds if future layer-operation exceptions must be retried. Current close/dispose guards prevent stale WebView callbacks, active I/O retains its response bounds, and these observations do not block the demonstrated repair.

## Follow-up: production viewport and view ownership

Root subsequently found a separate production-layout failure on the S24: the WebView viewport was 384 by 628 pixels, but `html`, `body` and `#map` reported zero height despite 902 decoded/renderable features. The isolated map harness above did not expose this composition/layout case. Its successful tile and marker evidence must not be presented as proof that the production container was visible.

Independent review of the frozen follow-up source found **no blocking rendering-lifecycle or security issues**. `map.css` gives `html`/`body` explicit viewport height and positions `#map` across the viewport, with both `100vh` fallback and `100dvh`. It no longer depends on a percentage-height ancestor chain. Native clipping bounds the Android view within its Compose allocation.

`MobileLiveMap` now creates the WebView only inside the `AndroidView` factory and releases it through `onRelease`, avoiding a remembered view that can outlive or be destroyed independently of its owner. Page startup is posted only after attachment and positive width/height; repeated attachment/size callbacks are guarded by `started` and cannot reload the page. Pending native state is retained until page completion. Detachment removes the startup callback; release marks the view disposed before canceling callbacks, closing its network owner, stopping loading, clearing pending data and destroying the view. Recomposition updates the current selection callback without opening a second authority path.

Native nonzero size changes signal the existing local JavaScript function. Its `ResizeObserver` and window resize handler coalesce work through one animation frame, skip zero dimensions and unchanged dimensions, then resize MapLibre. Canvas changes do not change the outer container dimensions, so the comparison prevents a resize feedback loop. The existing dirty-state/style/idle mechanism still delivers the most recent phone state after style readiness. These changes introduce no external URL, arbitrary native command, persistent state or location logging.

Release protections remain present in product source: `MainActivity` sets `FLAG_SECURE` before content creation, excludes autofill/content capture, and does not enable WebView debugging; release `isDebuggable` remains false. The WebView still blocks default network loads, file/content access, cookies, DOM storage and mixed content, cancels TLS errors, and serves only its exact local asset allowlist plus bounded fixed-provider map paths. The production repair does not weaken these controls for visual testing.

The reviewed startup policy test checks that construction and unattached layout do not load a page and that attached nonzero layout does. Mobile owner reports 14 policy and 17 rendered tests passing for this follow-up. The reviewer separately ran `node --test tools/tests/mobile-map.test.mjs`: one test passed, including zero-height rejection, transition to a 628-pixel viewport, animation-frame coalescing, unchanged-size suppression and deferred native state/marker rendering. This is synthetic lifecycle/JavaScript evidence. Root's exact-code phone capture and final release build remain the source of subsequent hardware/release qualification.

## Final addendum: bounded pixel fallback and secure release

The subsequent actual-phone check showed that CSS viewport units alone still resolved to zero in this composition case, despite a positive `window.innerHeight`. The final source therefore also sets `html`, `body` and `#map` dimensions to numeric viewport pixels inside the existing coalesced resize callback. Independent source review confirms that both values must be finite, strictly positive and no greater than 32,768. Only numeric values are concatenated with `px`; no query, coordinate or provider text enters a CSS property. Style properties are written only when changed. The existing positive-dimension and changed-client-dimension checks still guard `map.resize`, and clean state revisions still suppress idle redraws. This fallback introduces no resize/idle feedback loop or new security boundary. **No blocking findings.** The earlier CSS-only assessment establishes source intent, not a successful standalone hardware fix.

The updated VM regression models zero CSS height with a 628-pixel window, verifies restoration to `628px`, and retains the coalescing/unchanged-size/deferred-state checks. Root's final record, `.build/global/v06-actual-phone-render-result.json`, distinguishes the diagnostic same-package UI candidate from the secure release. The candidate rendered public Chicago streets, route and markers with 1,558 features and a 628-pixel canvas; gear/Settings/Map return, keyboard shrink to 318 and restoration, and background return passed without injected final layout fixes. Capture/debug exceptions were limited to that diagnostic candidate.

Root reports the final signed APK was installed through the bundled desktop, with installed bytes matching `1ad5c7049c4c8ad52d89700c71873d72ebcb995257fbb623ed045fb6d14019e7`. The actual production window restores `FLAG_SECURE` (`0x2000`), exposes no WebView debugging socket, and its DEX contains no `setWebContentsDebuggingEnabled` call. The owned debugging forward was removed and the final secure gear menu hierarchy passed. These facts are recorded by root rather than independently repeated by this reviewer. Secure-release screenshots remain black as expected, so visible map pixels are candidate evidence, not a captured secure-release assertion. Final verification reports 160 Android tests and 107 Node tests passing. Physical spoof playback and radio transitions remain unqualified.
