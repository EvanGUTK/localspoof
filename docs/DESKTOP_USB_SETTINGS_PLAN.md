# Windows USB connection and session settings plan

Status: implementation authorized by the user's direct build request; ECC planning and independent security review accompany implementation. The expanded Android responsive-UI request makes the final combined release target desktop 0.3.0 plus Android companion 0.3.0, retaining the existing Android signing identity. The initial USB-only plan used Android 0.2.0 as its qualification baseline; the final desktop must verify and bind the new 0.3.0 companion. No physical-device install, pairing, radio change, or mock-location activation is authorized by this plan alone. Root owns packaging and qualification; this review agent owns this document only.

## Problems and intended behavior

The Windows desktop must discover an installed Android SDK without running discovered executables until the user starts phone setup, start a local ADB server when none is running, recognize an attached physical phone even when Windows ADB returns `unknown` for its device path, and install the verified companion for the supported primary Android user without also attempting protected profiles. Failures must describe the next useful user action without exposing raw subprocess output.

Speed entry and session preferences must be useful without creating a persistent profile. The UI supports mph, km/h, and m/s; the Android protocol and route engine retain meters per second. Defaults and map display preferences live in memory for the current window.

## Official-source findings

* AOSP `socket_spec.cpp` recognizes a TCP host as local only when its host is empty or `localhost`. The client refuses to start a daemon when a supplied socket is classified remote. Consequently, `-H 127.0.0.1` and `-L tcp:127.0.0.1:5037` can connect to an existing local daemon but fail a cold start. Use the explicit server socket `-L tcp:localhost:5037`, clear remote-server environment variables, and never request `-a`. The application's forwarded phone connection remains literal `127.0.0.1`.
* AOSP `get-devpath` returns `unknown` when transport device-path metadata is empty. Missing metadata is not a transport classification. AOSP's device tracker protobuf independently labels transports `USB` or `SOCKET`.
* AOSP `format_host_command` prioritizes `-s` over `-d`. A sole-physical-phone fallback must run `-d get-serialno` **without** `-s` and require exact equality with the selected serial. It then fails closed if multiple physical USB transports exist. Present Windows PnP USB devices with an exact serial can corroborate attachment, but PnP presence alone cannot prove that a selected ADB transport is USB. A future bounded first-snapshot device-tracker reader can support several attached USB phones without weakening that distinction.
* AOSP package installation defaults to `USER_ALL`; session creation adds `INSTALL_ALL_USERS` for that default. Explicit `--user 0` limits this build's installation to its supported primary-user phone workflow. Do not assume that user ID 150 identifies the same kind of profile on every device. Do not remove profiles, change their restrictions, or retry installation for all users.
* Actual Windows qualification exposed binary corruption in the generic `adb shell -T` stdin path. A successful `exec-in` process alone is also insufficient because that mode does not deliver installation success to the caller. AOSP's streamed installer instead opens an `exec:cmd package` service, copies binary bytes, and reads the package manager's status. Mirror that narrow protocol over the fixed local ADB smart socket: bounded transport selection, fixed install command, original hash-verified bytes, explicit success response, and total operation deadline. Do not expose a generic smart-socket or command service to the webview.

## Implementation boundaries

1. **Tool discovery and companion packaging.** On an explicit setup action, read `ANDROID_HOME`, `ANDROID_SDK_ROOT`, the usual `%LOCALAPPDATA%\\Android\\Sdk` directory, and a bounded number of PATH entries. Accept only absolute existing `adb.exe`/`adb` candidates. Discovery never executes a tool or recursively scans disks. Keep manual path entry available. Ship only the release APK whose package, release version, non-debuggable state, signer certificate, and bytes were verified by the desktop build script. Hold the source and staged APK read handles against replacement throughout packaging; rehash the stage. At runtime rehash and install those same in-memory bytes, with a bounded size, through the selected device.
2. **Local ADB and physical USB.** Use a fixed explicit local server socket, clear ADB trace/remote endpoint/serial overrides, disable automatic mDNS connections, and preserve exact serial selection. Reject emulator and network-style serials. Accept positive USB metadata; handle Windows `unknown` only through independently demonstrated USB transport selection. Bound native PnP enumeration, subprocess output, and deadlines. Never invoke `kill-server`, use wireless transport as fallback, or expose a generic shell launcher.
3. **Companion installation.** Preserve the streamed, hash-verified APK installation and add explicit primary-user targeting. This build targets supported user 0 explicitly; it does not detect or automatically select another active user. Nonzero-user support needs a future explicit policy. Use binary smart-socket streaming rather than the Windows shell stdin path. No uninstall, downgrade, permission grant, or profile bypass occurs automatically.
4. **Actionable errors.** Return a fixed allowlist of typed error categories for tool absence/failure, unauthorized/offline devices, USB-only rejection, install user restrictions, incompatible existing signer/version or Android SDK, insufficient storage, timeouts, and untrusted APKs. UI text must explain a concrete next action. Raw stdout, stderr, serials, account/profile names, file paths, and Java exceptions never become diagnostic logs or public errors. Unknown responses remain generic failures. Read-only setup discovery and physical-phone status must not be described as completed phone installation or verified playback.
5. **Units and preferences.** Convert mph with exactly `0.44704` meters per second and km/h with `1/3.6`. Retain the canonical physical speed separately from rounded display text so repeatedly changing units does not modify a prepared route or accumulate drift. A real speed edit or mode-default application invalidates the prepared preview. Validate finite values and the existing per-mode engine bounds after conversion. Defaults are mph/miles with configurable walking and driving presets. Additional preferences cover route autofit and optional following of phone playback. Reset defaults restores fresh in-memory defaults. Clear preview removes coordinates, routes, query/results, airport selections, and journey state while retaining these non-activity preferences until the window closes. Stop/disconnect restores the selected journey's speed from the current mode preset. Do not use localStorage, settings files, analytics, recovery sessions, or history.

## Verification and review gates

* Native tests cover the exact local socket argument prefix, scrubbed remote overrides, physical USB positive/unknown/negative behavior, exact serial matching, ambiguous USB rejection, fixed install `--user 0`, hashed-byte streaming, and typed sanitized failures. Smart-socket tests cover hexadecimal framing, OKAY/FAIL status bounds, binary bytes including NUL/newline/control characters, premature close, timeout, oversized diagnostics, and failure without an exact success line. Windows-only USB enumeration and binary installation need real Windows qualification in addition to pure parsing and Unix subprocess tests.
* UI tests cover all three conversions, repeated unit changes preserving canonical speed and prepared plan, per-mode bounds, invalid edits invalidating a plan, mode presets, reset defaults, temporary preferences, discovery without execution, and sanitized setup messages. Clear erases flight preview selections while an active committed USB flight remains controlled by the authenticated phone's radio request and native ownership checks, independent of the editable preview radio selector.
* Shell tests cover untrusted APK/signature/package/debuggable rejection, stale trust environment rebuilds, bundle mapping and resource availability, and runtime hash rejection if the companion differs. Review the resolved resource path and its bounds without adding general filesystem access.
* Run existing frontend tests/type checking, native tests and Clippy, desktop shell tests and Clippy, then build the verified Windows NSIS installer. Desktop preview and read-only device enumeration can be qualified independently. Report actual device installation, pairing, screen-off playback, Stop, radio control, and profile behavior only after separately authorized physical-device tests have run.

## Explicit limitations

This change does not guarantee support for protected profiles, managed Android devices, nonzero primary/headless-system-user arrangements, multiple attached physical phones under a sole-USB fallback, or arbitrary third-party apps accepting Android mock locations. Automatic radio changes retain existing phone capability and ownership checks. The global online map and route providers retain their existing network/privacy disclosures and limits; these settings changes add no location storage or telemetry.

## Independent ECC source review

The final reviewed source includes exact USB transport corroboration for Windows unknown paths, a phone Hello before reporting a connected control service, and scoped forward cleanup on failed handshakes. The binary installer is private to the native crate; its services are fixed, its destination is literal IPv4 loopback, and its bounded reads/writes recompute a single absolute deadline. Runtime installation reuses the same byte buffer that passed the trusted desktop build hash. Discovery and Tauri resource bundling preserve manual paths and artifact trust without exposing generic filesystem or command permissions.

Review found and coordinated fixes for native/UI error-code mismatch, an installed-app signer conflict incorrectly described as an untrusted supplied file, APK-only discovery incorrectly suggesting ADB was ready, and Clear retaining airport selections. A subsequent Clear radio-selector reset initially disabled live USB flight polling; polling now uses the authenticated phone's committed radio request and native capability/phase/ownership checks, independent of editable preview fields. Canonical m/s remains separate from display text, temporary preferences use no persistence, and invalid speed edits cannot recover an old prepared plan through a unit switch. No remaining source blocker was identified. Root's final Windows build and actual device qualification results belong in the build/validation documents, rather than being inferred from this source review.
