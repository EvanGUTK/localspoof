# ECC code review

Reviewed 2026-10-02 using ECC's `agents/code-reviewer.md` checklist. Scope: plain Kotlin domain and tests, desktop UI/contracts, Gradle pins, and Android domain/service call sites. Domain and desktop source were reviewed independently of their authors; Android lifecycle findings also include self-review of the Android implementation. The workspace has no Git repository, so review used complete source files rather than a Git diff. No commits were created.

## Findings and resolutions

| ID | Severity | Original location | Concrete trigger and outcome | Resolution |
|---|---|---|---|---|
| C1 | HIGH | `android/session-domain/.../Session.kt`, `advanceFlight` | Airports can be up to 250 m from snapped road nodes. Origin arrival assigned the catalog centroid, and the destination leg restarted from its road node, causing unsupported jumps and ground-speed spikes. | Fixed in source: holds and arrival placement use complete precomputed road-access endpoints. Preview explicitly exposes `originAirportAccessPoint` and `destinationAirportAccessPoint`; APK and desktop disclose them. Added domain regression specification with airport centroids about 100 m from road nodes. Kotlin execution remains pending. |
| C2 | HIGH | `desktop/ui/src/app.ts`, PreparePlan handler | UI expected `points`, `distanceM`, `durationSeconds`, and departure/arrival names, while phone emitted `geometry`, `distanceMeters`, `durationMs`, and origin/destination names. Every preview lost geometry and itinerary details. | Fixed: dedicated `decodePreview` consumes the canonical phone fields and validates coordinates/durations. Executed TypeScript regression passes. |
| C3 | HIGH | `android/session-domain/.../Session.kt`, instant `buildPlan` branch | The corrected desktop decoder rejects an empty geometry; instant preview used the default empty geometry, disabling every desktop instant start. | Fixed: instant preview contains its single destination coordinate. Desktop single-point regression executed and passes; domain specification added, execution pending. |
| C4 | MEDIUM | `android/session-domain/.../Session.kt`, `tick` and `snapshotLocked` | Time spent waiting for manual radio changes or provider placement acknowledgment consumed the estimated journey duration; after a long wait, remaining time incorrectly became zero during a fresh flight interval. | Fixed in source: external waits do not advance simulated travel elapsed; remaining duration is unknown during those waits. Added domain regression specification, execution pending. |
| C5 | MEDIUM | `android/session-domain/.../Session.kt`, `advanceGround` | Each integration step clipped travel at an edge endpoint and discarded the remaining step time. Dense 0.1 m vertices reduced a requested 10 m/s route to roughly 1 m/s. | Fixed in source: consume only time needed to reach the edge/dwell boundary and carry remaining time into the next edge. Sparse/dense path equivalence regression specified, Kotlin execution pending. |
| C6 | MEDIUM | `desktop/ui/src/app.ts`, `refreshControls` and Stop handler | A prepared replacement could not be committed during ACTIVE playback. Successful Stop also left polling live, which overwrote radio-recovery instructions with an unexpected disconnect message. | Fixed: valid prepared plans can be committed during active playback; Stop performs expected connection teardown and preserves the phone's static recovery message. Browser/native interaction remains pending. |
| C7 | HIGH | `android/app/.../MainActivity.kt`, Stop handler; `SimulationService.kt`, cleanup | The activity remains bound while visible. Calling only `stopService` does not destroy a service until bound clients detach, delaying socket/foreground cleanup after local Stop. | Fixed: revoke and Stop the domain first, explicitly invoke the service's STOP path, cancel its ticking scope, close socket, remove foreground notification, detach the runtime, and unbind the activity. Remote/notification Stop also publishes `serviceRunning=false`, which releases a visible activity binding. Structural assertion passes; Android lifecycle execution remains pending. |
| C8 | HIGH | `android/app/.../SimulationService.kt`, ticking notification and Stop paths | Coroutine cancellation does not interrupt an already executing synchronous tick. That tick could publish a notification after Stop removed the foreground notification. Repeated Stop or delayed destruction could also stop a subsequently created session through the global runtime. | Fixed: a small lifecycle lock protects stopped-state checks, notification publication and foreground removal; heavy domain ticking remains outside this lock. Stop claims an idempotent first-transition flag before cleanup; a stopped instance rejects subsequent starts, binding to a stopped instance immediately unbinds, and delayed `onDestroy` does not repeat runtime Stop. Foreground-start failure enters the same cleanup path. Structural assertions pass; scheduling/lifecycle device execution remains pending. |
| C9 | MEDIUM | `android/app/.../MainActivity.kt`, current-position and place-result actions | After preparing a route, choosing a new current origin or place destination changed displayed inputs without invalidating the old prepared ID. Start could therefore launch the previously prepared route. | Fixed: both actions clear `preparedId`, matching manual coordinate edits and requiring a fresh preview. Structural assertions pass; Compose interaction remains pending. |
| C10 | HIGH | `android/app/.../SimulationService.kt`, synchronous settings read; `RuntimeModel.kt`, ticking entry | An old coroutine can pass its cancellation check, block in a synchronous settings read, and return after a successor service attaches. Its global ticking or error cleanup could then mutate/inject into the successor's session. | Fixed: the coroutine captures its own immutable provider instance. `RuntimeModel.tick` checks provider identity and service-running status inside the runtime lock before all effects. Settings-error handling uses an equally guarded `failOwner` path, so stale failures cannot clear or publish errors into a successor. Playback remains outside the notification lifecycle lock. Structural assertions pass; adversarial Android scheduling execution remains pending. |
| C11 | MEDIUM | `android/app/.../RuntimeModel.kt`, Stop recovery message | A USB radio operation can finish after phone Stop but before its changed setting was observed, leaving no observed radio debt from which to produce recovery guidance. | Fixed: Stop captures current flight mode and USB policy before clearing them. Active USB flight Stop always shows static manual airplane-mode checking guidance, including when provider cleanup fails, and repeated Stop preserves it. No automatic radio toggle or persistent recovery record is added. Actual in-flight ADB/Stop ordering remains a physical-device qualification case. |

Android's documented [combined started/bound service lifecycle](https://developer.android.com/develop/background-work/services) confirms that stopped services with bound clients wait for unbinding before destruction. C7 therefore releases resources explicitly instead of relying on `onDestroy` timing.

## Validation actually executed

- Initial independent model review: **PASS, 12 tests**. Subsequent targeted fixes expand this to **14 passing model tests**, plus four passing mock-DOM tests in the builder's final verification. Coverage and final commands are recorded in [VALIDATION.md](VALIDATION.md). These cover coordinates, antimeridian projection, route controls, strict flight threshold, resource normalization/bounds, Unicode chunks, canonical previews, instant hold preview, airport access coordinates, ADB paths, boarding controls, and delayed/canceled UI work.
- `node tools/check-protocol-fixtures.mjs`: **PASS**. Six synthetic JSON response fixtures agree with Android source field names; public fixtures omit activity state; source assertions check explicit service Stop, activity unbinding, notification/Stop synchronization, idempotent teardown, preview invalidation and service-owner guards before tick/error effects. This is structural evidence, not execution of Kotlin, USB transport, or Android callbacks.
- XML parsing and manifest assertions: **PASS, four XML documents**. No internet permission, backup disabled, private location foreground service, and mock-app selection declaration confirmed.

Gradle pins are internally consistent with the official [AGP 8.11 compatibility table](https://developer.android.com/build/releases/agp-8-11-0-release-notes): Gradle 8.13, JDK 17, and API 36. Kotlin Android/JVM/Compose plugins all use 2.2.21; the Compose compiler plugin follows the [official migration rule](https://kotlinlang.org/docs/compose-compiler-migration-guide.html). Domain tests use JUnit Jupiter and `useJUnitPlatform`; app pure tests use JUnit 4.13.2. No additional definite compile errors were identified in source review. This is not a compilation result.
