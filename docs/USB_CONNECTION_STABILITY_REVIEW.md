# USB pairing idle-time fix and remaining stability boundaries

This record describes the 0.3 idle/read and local-I/O fixes and their historical public-Hello qualification. The subsequent 0.4 source replaces typed-secret pairing and fixes refresh closing the listener; see [approval pairing plan/review](USB_APPROVAL_PAIRING_PLAN_REVIEW.md) for the current contract and its separate delivery evidence. The old Hello result does not establish the new approval flow.

Independent source review of `ControlFrameReader.kt`, its connection deadline helper, and `PhoneControlServer.kt` passes. This is a fix for a reproducible idle-before-pairing disconnect; it is not a claim that every possible disconnect has been eliminated.

## Root cause and narrow fix

The previous server began a five-second header read immediately after a public Hello response. Windows did not start its polling loop until Request pairing, so a user taking more than five seconds to enter the secret could lose the socket and have the secret revoked. Five seconds intended to bound a partially arriving frame was also bounding an entirely idle connection.

The replacement waits for readiness on the exact accepted LocalSocket file descriptor with `Os.poll` in slices of at most one second. Idle checks inspect/expire the lease under the session lock and never authorize a request or update `lastSeen`. The preauthentication connection window is bounded to 120 seconds from acceptance; the pairing secret's own existing expiry is separate and unchanged. Once bytes are ready, one absolute five-second deadline covers the header and entire payload. Connection and frame budgets are checked before and after each bounded read; invalid lengths are rejected before body allocation. EOF, socket errors, cancellation, and protocol failures close the accepted socket through the existing cleanup path and revoke only its matching controller generation.

Readiness polling is deliberate: Android's native LocalSocket read implementation throws a plain IOException for negative receive results, including timeout errno, so catching only SocketTimeoutException would incorrectly treat idle timeout as a fatal socket error. Sources: [AOSP LocalSocket JNI read behavior](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/jni/android_net_LocalSocketImpl.cpp) and [Android Os.poll](https://developer.android.com/reference/android/system/Os#poll(android.system.StructPollfd[],%20int)).

## Authorization remains strict

The existing six-second approved credential lease is unchanged. Poll readiness and public Hello calls do not renew it. `ControlConnectionDeadline` remembers an observed approved credential, so expiration/revocation cannot reopen that connection's longer preauthentication window. Actual operations still require the current matching token/session and increasing sequence and run the existing expiry checks; no new pairing or mutation bypass was introduced. A frame already in progress is independently bounded by its five-second frame timeout, and dispatch refuses credentials that expired while it was arriving. Phone Stop retains its synchronous revocation and socket shutdown.

Nine deterministic reader/real-lease tests cover idle longer than five seconds, fixed preauthentication limits, partial headers, fragmented/slow-drip payloads, connection expiry during a frame, approved-lease expiry/revocation, cancellation, bad lengths, and truncated frames. Root reports these tests passing in the final 53-app/37-domain Android run. Root also reports Android 0.3.0 installed on the same S24, with a public Hello succeeding before and after eight idle seconds on the same socket. This confirms the previously failing idle interval; it does not establish real pairing, sustained authenticated use, Stop, or radio behavior, and no pairing secret, mock-location operation, or radio change was used in that check.

## Desktop busy-heartbeat audit

The desktop two-second polling loop intentionally skips its normal heartbeat while `busy`. Independent-heartbeat paths run during online route acquisition (`onlinePlanning`) and selected asynchronous local file work, which run outside the native phone bridge lock. Authenticated phone commands and GeoPack transfer chunks also renew the lease when authorized, so ordinary quick actions and progressing transfers do not require a separate heartbeat for every step.

Review identified lease expiry during slow paired local PMTiles loading or asynchronous GeoPack reads/hashing. The final source addresses those independent waits with a narrow `localIO` helper wrapping only `file.text`, `crypto.subtle.digest`, and `world.setOfflineArchive`. A local owner carries the activity epoch and identity; one owned heartbeat promise prevents duplicate requests. The helper closes its keepalive window and awaits an already-sent heartbeat before a later phone mutation captures the current revision. Stop/disconnect clear ownership and invalidate stale callbacks; Clear invalidates preview ownership so a delayed file result cannot apply or upload cleared activity.

Eight new deterministic desktop regressions cover delayed file completion, Stop, Clear, lost lease, hashing, PMTiles loading, draining a heartbeat before importing with revision 7, and no heartbeat queuing during the phone import itself. Root reports the full desktop test count increasing to 59. Independent source review passes this scoped change; no new credential lifetime or native concurrency authority was introduced.

A meaningful residual remains: a long native phone planning/import operation can exceed six seconds while the native bridge mutex and sequential phone handler prevent another heartbeat from being processed. Synchronous renderer work, event-loop suspension, or machine sleep can also prevent timers from running; an async keepalive flag does not fix those cases. Phone playback may continue after controller access expires, but Windows must reconnect and obtain fresh phone approval.

A generic "send heartbeats whenever busy" change remains unsafe: a heartbeat queued behind CommitPlan can carry an outdated expected revision and trigger a false disconnect, and queued heartbeats cannot rescue a sequential handler already blocked by a long command. Longer native operation scheduling requires a separate design/qualification step. Do not claim that all busy-operation, background scheduling, cable, driver, or OEM disconnect causes are resolved.

## Final observed reconnection

After a later ADB transport disappearance with the Windows ADB interface still present, the user reported reconnection. Root verified exactly one authorized physical phone and completed all 15 final native desktop settings/USB checks, including auto-discovery, public Hello and disconnect cleanup. The cause of that transient host/phone transport loss remains unqualified; no shared ADB daemon was killed and no credentials, simulation or radio changes were used.

## 0.4 installation and host transport investigation

Root later installed the signed 0.4 APK through the production verified-byte native installer and opened the phone app; the user enabled desktop control. Actual Windows QA passed eight settings checks before scanning again found zero ADB devices. Six diagnostic samples showed one present/ready Windows ADB interface but zero ready ADB transports. This is a host/phone transport disappearance, separate from the app's secret-refresh listener closure. Subsequent recovery/approval evidence follows below.

Official Platform Tools 37.0.1 release notes document the new Windows `libadbusb` backend and `ADB_USB_LEGACY=1` fallback. See [SDK Platform Tools release notes](https://developer.android.com/tools/releases/platform-tools). Root confirmed that SDK version/backend and performed one controlled process-only legacy startup, after checking the exact official SDK server path, zero devices, zero forwards and a single loopback listener. That restart exposed one **offline** transport rather than zero devices; it did not establish a ready/authorized transport or successful comparison/approval.

The subsequent native Windows source sets `ADB_USB_LEGACY=1` only in the launched ADB process environment. This selects the compatibility backend when that client starts a new daemon; it cannot change an already running shared daemon. Scanning never kills/restarts the shared server. Remote-server, trace and inherited serial environment exclusions remain in place, and the local listener remains explicitly scoped. No persisted user environment, registry or driver change is reported. This review performed no daemon restart and does not claim sustained USB reliability or resolution of every disconnect.

In subsequent 0.5 development, a deterministic regression reproduced an old cancelled route result clearing a newer paired preview's keepalive flag. The scoped fix replaces that shared boolean with an epoch and unique owner identity; an old completion cannot clear a successor, and only a matching-epoch heartbeat is drained before mutation. The independent regression passes. This changes ownership of an existing keepalive window, not credential deadlines or simultaneous native phone mutation rules.

After user reconnection with the compatibility backend, root observed an authorized physical S24 and Windows 0.4 completed all 15 native settings/live-USB checks plus eight real approval checks. Matching comparison and explicit phone consent passed; native retained the credential, comparison cleared after approval, unpaired Start stayed disabled, ten seconds of approved heartbeats and explicit disconnect cleanup passed. No journey/radio operation or coordinate logging occurred. This bounded recovery and interaction result does not establish sustained reliability or prove that the backend change alone caused recovery.

Fresh 0.5 signed installation and 12 actual phone approval/fresh DEVICE-dot checks also pass, including ten seconds of approved heartbeat and explicit disconnect clearing. No mock journey or radio operation was used. See [validation](VALIDATION.md) for that version-specific evidence; this still does not establish sustained USB reliability.
