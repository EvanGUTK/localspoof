# 105 — smoother phone Follow, standalone Android, wireless control and updates

Created 2026-10-04 as a read-only plan. Writable implementation began 2026-10-05 after the user requested work on this MD and selected **public signed distribution**. Baseline: LocalSpoof 0.7.0, protocol minor 6, commit `70b3ed8`. Read [104WORK](104WORK.md), [0.7 implementation](HANDOFF_0_7_SOL_6_1.md) and [validation](VALIDATION_0_7.md) first. Implementation targets 0.8.0 / Android code 8; protocol minor 6 remains compatible. Qualification and final publication are recorded below.

## Requested outcome and priorities

1. Fix Android Follow: the user reports the camera lets the dot travel, then catches up with a jump; desktop feels smoother.
2. Make Android a complete standalone app for planning and playback, retaining Windows as an optional interface to the same phone-owned journey.
3. Add Android's authenticated wireless-debugging ADB connection alongside USB, with setup inside the desktop interface.
4. Add signed in-app updates on both platforms, avoiding repeated manual downloads, uninstalls and setup. Keep user data local, with no account or hosted application backend.

Deliver Follow first. Treat standalone planning, wireless transport and update distribution as separate milestones with independently reviewable behavior. Sensor spoofing, EV charging and Life360 compatibility guarantees remain outside this scope.

## A. Phone Follow — investigate and fix the actual jump

The reported behavior is a new defect. Previous 0.7 checks established visible controls and map return; they did not physically qualify smooth moving Follow. Read-only OpenMob inspection found the S24 connected and the phone displaying **Following**. No interaction, test route or movement reproduction was performed. Production blocks screenshots, so this inspection supplies UI-state evidence rather than pixel evidence of the reported jump.

Source observations, not a confirmed diagnosis:

- [Android motion tracker](../android/app/src/main/assets/mobile-map/motion.mjs) interpolates between confirmed fixes. A new animation begins at the previous acknowledged point; [desktop motion](../desktop/ui/src/motion.ts) starts at the currently displayed interpolated point. Their duration and continuity thresholds also differ. Overlapping updates can therefore behave differently.
- Android duplicate-sample handling refreshes its receipt time; inspect whether the next genuinely new sample is judged against an artificially short interval and loses continuity.
- The Android tracker clears animation whenever `setVisible` runs. [Map visibility replay](../android/app/src/main/assets/mobile-map/map.mjs) invalidates rendering, resizes and reapplies motion on a visible-state call. [The WebView bridge](../android/app/src/main/kotlin/dev/localspoof/android/MobileMapView.kt) can invoke this during replay. Verify redundant visible/replay calls rather than assuming they occur continuously.
- Camera following uses `jumpTo` during display updates, and each `moveend` can report a viewport through the WebView bridge. Inspect callback frequency, Compose recomposition, geometry replay, main-thread work and tile/GeoJSON work. Repeated camera commands, a stalled renderer and late provider samples are distinct faults.

Proposed design:

- Keep provider cadence and display cadence separate. Phone runtime emits immutable acknowledged motion with sequence, sample age, placement generation and phase. One renderer animation loop drives the displayed dot and camera from the same displayed position.
- Start interrupted interpolation from its current displayed point toward an already acknowledged target. Bound delay; never extrapolate unsubmitted movement, silently snap an off-route fix onto a line, or hide a genuine stale fix.
- Make visibility idempotent. Rebuild/replay geometry only for actual geometry or lifecycle changes; ordinary telemetry must not refit the route or recreate the renderer.
- Coalesce viewport reporting and WebView messages. Avoid routing every animation-frame camera change through Compose. Camera memory and nearby-search viewport have different update needs; panning alone must not issue searches.
- Keep user zoom, route projection and usable map center above the bottom sheet. Drag disables Follow; explicit Follow recenters; Fit stays an overview. Respect reduced motion. A phase change, explicit jump or stale recovery must be distinguishable from ordinary movement.
- Diagnose with bounded RAM-only timing counters: sample age/sequence, bridge latency, display-frame intervals, camera updates, geometry rebuilds and lifecycle events. Do not add production logs or location history.

Acceptance: on the user's chosen route, compare phone and desktop simultaneously for Walk, Drive and timed Fly, including variable/high speeds, corners, holds, pause, drag/recenter, Settings return, rotation and renderer recovery. With fresh continuous samples and no user drag, the camera must not sit still then periodically catch up. Record actual frame/camera behavior and sample freshness separately. Establish S24 performance targets from a measured baseline; do not promise a universal frame rate before testing. Use OpenMob observation → plan → act → verify in the future writable session; unrelated geographic tests belong in an emulator.

## B. Standalone Android with optional Windows interface

The phone already owns mock submission, foreground playback, acknowledgments, radio observations, stops and accounting. The missing major standalone capability is worldwide online road/automatic-station planning, currently supplied by Windows. Extend the existing app and domain rather than create another APK with a competing provider/session.

### Logical boundaries

| Component | Responsibility |
|---|---|
| Phone session domain | Authoritative active journey, remaining edits, validation, radio gates, stop timers and Vacation ledger |
| Phone planning coordinator | Current-point snapshot, cancelable provider work, bounded previews, held-point replanning and stale-result rejection |
| Android data adapters | Online roads/search/places, eligible airports, US vehicle/reference data and station detours; explicit offline/manual fallback |
| Mobile presentation | Map, compact route sheet, saved items, gear, Follow, ETA/speed/cost and local Start/Stop |
| Windows controller | Optional larger planner/editor using the existing authenticated contract; never a second playback engine |
| Connection adapter | USB or authenticated wireless ADB, below the same controller protocol |
| Update coordinator | Trusted release discovery, download, verification and safe platform installation; no journey authority |

Keep these boundaries small; introduce build modules only when needed. Domain remains pure Kotlin. Existing ECC Android Clean Architecture guidance applies; do not introduce a database or account for planning.

Android flow: search/map/bookmark → Teleport or Route → Walk/Drive/Fly → compact options → Preview → phone Start. Full standalone parity includes upcoming stops, remaining destination/airport changes, Undo, timed pause, eligible airports, variable speeds, Vacation fuel/hotel estimates and saved choices. Providers remain honest about missing coverage, road access, prices and specifications.

Port bounded online planning into native Kotlin adapters using the same typed requests and policy as Windows: call/time/body/geometry limits, reserve-aware road detours, cancellation, attribution and actionable errors. Android preview and Start must work with no desktop installed, connected or discoverable. Keep current RAM-only caches; explicit bookmarks and user-imported offline assets remain local. A world basemap is not a full-planet offline road graph. Online coverage is not exhaustive Google/Apple place coverage.

Standalone does not require ADB or a desktop toolchain. The user still selects LocalSpoof as the mock-location app and grants relevant permissions. Keep the existing foreground location service and visible Stop notification; start playback from visible UI and qualify screen-off/battery behavior. Android's foreground-service rules still apply. [Official foreground-service requirements](https://developer.android.com/develop/background-work/services/fgs/service-types).

One phone session must work through local UI or an explicitly approved desktop. Connecting never replaces or restarts an active plan. Snapshots reconcile both interfaces. Local Stop and later user intent win; conflicting editor ownership gets a clear response. Taking over a controller-owned edit requires an explicit supported action, not silently applying simultaneous drafts. Desktop loss leaves phone-owned playback available. Planning may run on either client; the phone validates every submitted plan. Reuse 104's remaining-edit/ledger/radio invariants.

Standalone flight uses phone prompts for real airplane-mode gates; do not depend on a desktop to restore connectivity or assume the APK has privileged radio control. Fetch required departure/arrival roads before entering an offline air leg. An in-flight destination change requiring unavailable online data waits or offers supported offline/manual planning; it cannot invent a road route or bypass the restoration gate. Live submission still does not prove Life360 receipt.

Acceptance: with the PC disconnected, plan and play each mode, edit remaining travel, complete fuel/hotel holds and stop cleanly. Then connect Windows to that existing session, approve, edit without restarting, disconnect and continue locally. Test provider failures and conflicting edits, along with small screens, large text, keyboard and orientation.

## C. Wireless debugging ADB

Use Android 11+ authenticated TLS wireless debugging on the same Wi-Fi network. Android supports QR/code pairing and retains workstation trust until revoked. The S24 observed here runs Android 16. Support its existing workflow; do not assume newer Android-only features. Older supported phones retain standalone/USB operation. [Official wireless debugging](https://developer.android.com/tools/adb#connect-to-a-device-over-wi-fi).

Expand [the existing wireless roadmap](WIRELESS_CONTROL_ROADMAP.md). Current production intentionally rejects network transports; do not simply remove that validation.

Desktop connection dialog: **USB / Wi-Fi**, current status, clear OS setup guidance, discovered authorized phones and a manual local-endpoint fallback. Automatically find/start the installed ADB tool and manage supported pairing/connect operations through bounded native calls; users should not need PowerShell. Prefer a tested QR pairing flow when feasible; retain a clear OS pairing-code fallback. Pairing and connection ports can differ and change. Do not invent a static port, read protected OS pairing secrets, or promise QR support before implementing it.

Discovery is opt-in and bounded. Treat mDNS names/addresses as untrusted hints. Validate local endpoint scope, authenticated device identity and the selected physical phone. Keep the workstation ADB server loopback-only and the application channel behind an owned forward to the existing phone-local endpoint. Keep USB's validation independent. Exclude arbitrary remote ADB servers, generic shell access and legacy open TCP debugging.

OS ADB pairing and LocalSpoof comparison-number approval remain separate. An OS-trusted computer is not automatically an approved app controller. Credentials remain native-only/channel-bound; no takeover or silent USB/Wi-Fi failover. Recovery refreshes phone state and requires appropriate fresh approval, preserving the journey. Detect the same phone exposed through both transports without creating two controllers. Manage only owned forwards/connections; ordinary retries must not kill a shared daemon.

OS/SDK workstation keys and trusted-device/network records persist outside the application's RAM-only activity boundary. Explain Android's Forget/revoke controls; clearing a journey does not erase that trust. Do not weaken shared privacy messaging to claim that no OS authorization is stored.

Airplane mode or Wi-Fi changes may remove the controller connection. Wireless flight must continue using phone-local radio prompts and Stop, with fresh approval after reconnection. Do not automatically enable Wi-Fi in airplane mode or promise remote restoration over a disconnected link. Test phone reboot, network changes, AP isolation, missing mDNS, revoked trust, wrong-device discovery, multiple phones, transport changes and actual flight connectivity loss.

Development OpenMob wireless pairing is a separate capability; its availability does not mean the production app supports wireless control.

## D. Signed in-app updates

### What users can expect

An update still installs new application binaries in place. The desired improvement is **no manual uninstall, repeated setup or hunting for downloads**. Add Gear → Updates: current version, Check for updates, release notes, Download, Install when ready, progress and retry. Preserve explicit saved items. Activity/approval remains RAM-only and is not made persistent by this feature.

The baseline 0.7 has no updater. One initial in-place upgrade must add the updater before subsequent releases can use it. It cannot receive this capability retroactively. No code hot-loading is planned; bundled code ships through signed application updates.

### Distribution without running an application server

Recommended: keep source in private `EvanGUTK/localspoof`; create a separate **public distribution repository** containing only signed installers/APKs, release notes and a static update manifest. The user authorized public signed distribution in the writable session; final artifact publication follows verification. Static files require hosting, but no custom backend, user account, route upload or cloud user-data store. GitHub releases are visible to repository readers; the private source repo cannot be an anonymous update feed. Never embed a maintainer token in clients. [GitHub release access](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases).

Alternative: another static HTTPS host; or explicit local-file import / trusted desktop-to-phone update transfer when no public host is wanted. Without any reachable distribution source or local transfer, remote updates cannot arrive. Git commits and AI edits alone do not update installations: build, test, sign and publish a release first. Release hosts may retain request metadata/IP addresses; this is separate from local-only user data.

### Windows

Use the official Tauri updater, a static version feed and its mandatory artifact signatures. Embed the public verification key; retain the updater private key separately from the Android key. Use per-user in-place NSIS upgrades with visible progress, a deliberate install/restart action and no unnecessary administrator prompt. Keep application data paths stable. Authenticode publisher signing remains separate from updater authenticity. [Tauri updater/signing/static-feed documentation](https://v2.tauri.app/plugin/updater/).

### Android

Use native PackageInstaller for a verified same-package upgrade. Keep `dev.localspoof.android`, the existing release signing identity and increasing version codes. Verify package/version/SDK compatibility, full signer identity and integrity before staging the APK; Android also enforces signing compatibility. No replacement key or debug-signed update for the installed release. [Android signing and upgrades](https://developer.android.com/studio/publish/app-signing).

The app needs the supported install-request permission and user trust for its installation source. Guide that setup and handle denial/cancellation. [Android install-source permission](https://developer.android.com/reference/android/content/pm/PackageManager#canRequestPackageInstalls()).

Android 12+ provides a conditional self-update path without an installation prompt, with explicit session policy, suitable target SDK and `UPDATE_PACKAGES_WITHOUT_USER_ACTION`, plus updater eligibility. Always support `STATUS_PENDING_USER_ACTION`; OS/version/ownership requirements can change. The reliable baseline is Download → Android confirmation → updated app, with no uninstall. Investigate the conditional path on the S24 rather than promise silent updates for all phones. [PackageInstaller user-action rules](https://developer.android.com/reference/android/content/pm/PackageInstaller.SessionParams#setRequireUserAction(int)).

### Trust, compatibility and safe timing

- Publish a bounded versioned release catalog: platform/architecture, version/code, minimum OS, protocol/capability compatibility, release notes, artifact URL, size/hash and verified signature. Android needs an authenticated catalog/artifact trust design using reviewed libraries; no homemade cryptography. HTTPS and a checksum alone are not the entire publisher-trust design.
- Preserve existing strict bundled-APK trust checks. A downloaded companion is a distinct trusted artifact verified against the signed catalog and original Android certificate; never accept an arbitrary URL/APK or the update server's unsupported trust claims. Standalone Android can update independently of Windows.
- Test old/new component combinations. Offer coordinated upgrades and actionable incompatibility guidance; partial upgrade cannot fall back to an insecure older protocol or start playback. Verify peer capabilities after reconnect.
- Download during a journey only if enabled and resource-bounded. **Install only at a safe idle boundary** after owned mocks are released, timers/control stopped and any changed radio state is restored or the unresolved restoration is explicitly handled on the phone. A paused flight is not a safe update boundary. Never silently end a journey, update midway or auto-resume after restart.
- Validate before changing the working installation. Interrupted/tampered downloads, wrong signer/platform, downgrade/replay and low storage leave the old app usable. Cleanup temporary downloads/install sessions after success, cancel, expiry and crash recovery.
- Bookmarks/schema migrations must be bounded and preserve supported data; do not erase user saves to recover an update. Keep current runtime coordinates, credentials and spent-fuel ledgers out of backups/migrations. Update metadata and temporary installation files are a necessary, explicitly bounded local exception; no telemetry or install-history database.
- Manual Check works without background polling. Offer opt-in startup checks/automatic downloads later, using conservative frequency and fixed public endpoints without device IDs, locations or activity in requests. Avoid a background daemon solely to check releases.
- Data-only catalog/reference-price refresh can be a separately signed versioned package. It must preserve manual overrides and affect new drafts only unless explicitly applied; never silently reprice/replan a live trip. Code changes still require application updates.

Acceptance: upgrade the current release in place on Windows and S24, preserve bookmarks/mock-app selection where the OS allows, handle Android permission and confirmation denial, cancel/retry bad downloads, reject signer/downgrade/compatibility failures, and prove installs are deferred through all active/paused/flight/refill/hotel phases. Verify clean owned-provider/radio cleanup before installation and require a new explicit Start after restart.

## Implementation record — 2026-10-05

### Follow

Three source-level failures reproduced before fixes: interruption restarted from the previous acknowledgment, duplicate receipts shortened the next animation interval, and redundant visible replay ended active animation. Regression tests now start from the currently displayed interpolated point, retain genuine sample cadence and preserve animation on idempotent visibility. Real hidden/resume lifecycle still expires stale fixes. The marker and Follow camera use the same displayed point, avoid per-frame viewport/replay work and preserve explicit pan/Follow/Fit behavior. This is regression evidence; simultaneous moving S24/desktop performance qualification is separately required and must use the user's chosen journey.

### Android planning

Native fixed-provider Kotlin adapters supply road geometry, phase-aware flight ground legs, reachable station detours and the official US year/make/model/reference-price flow. Online is the default and explicit imported offline assets remain selectable. Provider work is cancelable and bounded: planner 90 seconds/60 calls, per request 15 seconds, geometry 12,000 points. No fabricated posted limits, road connectors, station prices or tank sizes. Apply authority remains in the phone runtime; stale, canceled and phase-advanced results cannot replace the active plan. Generated fuel stops can be edited before Start, and explicit station choices survive remaining-route replan. Held road origin must remain within 0.1 m of the confirmed point; a provider snap to a different lane/path fails clearly and preserves the journey.

### Wireless control

Desktop provides USB/Wi-Fi selection, opt-in modern mDNS discovery, separate pairing/connection ports, a private-literal endpoint fallback and OS code entry through native stdin. SDK keys/trust persist under Android/ADB's own policies. Only RFC1918 IPv4 and unscoped IPv6 ULA endpoints are accepted; public/loopback/legacy ports, hostnames and scoped/link-local IPv6 are rejected. USB checks remain independent; bundled desktop APK installation and automated airplane control stay USB-only. Wireless flight uses phone prompts. No automatic transport takeover, generic shell IPC or shared-server reset.

A bounded CNXN/STLS preflight rejects genuine legacy sockets before SDK connect and before creating the owned app forward. SDK>=30, configured TLS port, enabled Wireless debugging and physical serial are checked with an absolute request budget. This preflight validates the modern endpoint behavior; it is not independent cryptographic attestation of the SDK's connection to a hostile custom peer. The official SDK owns TLS negotiation/trust, and LocalSpoof's comparison-number approval separately controls phone authority. QR pairing is deferred; manual Android pairing-code setup is implemented.

### Updates

Manual Gear → Updates checks a fixed public catalog and detached signature, with bounded verified downloads, progress, cancel/retry and explicit installation. Catalog max64KiB; APK128MiB; Windows installer256MiB. Both clients verify publisher authenticity, platform/version/protocol/URL/size/hash; Android also verifies same package and original full signer. Downloaded code is installed as a signed app upgrade, never hot-loaded.

Android PackageInstaller requires supported install-source permission and Android confirmation, with runtime reservation preventing Start while confirmation is pending. OS session reconciliation after process death fails closed until update sessions are absent. Safe idle requires stopped mocks/service/controller/timers/edits and completed radio/provider cleanup. Windows checks fresh authoritative phone safety when applicable, disconnects its own controller and hands verified bytes to the official Tauri installer. Cancellation doesn't silently Stop a journey. Temporary artifacts/sessions are disposable; explicit bookmarks remain local.

The official Tauri 2.9.0 updater is vendored with its licenses/archive hash and a small documented adapter for an already bounded, authenticated manifest. Additional reviewed patches remove runtime logging, reject installer launch failures and bound cleanup of owned installer stages. No updater plugin JavaScript capabilities are granted. Publisher tools re-verify original APK identity and pinned Windows signature/version before signing the exact catalog bytes.
