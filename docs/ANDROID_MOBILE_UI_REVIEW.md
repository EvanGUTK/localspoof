# Android 0.3.0 responsive UI review

Review status: independent source review of the Android 0.3.0 replacement passes; build and rendered/device qualification results remain owned by root. The implementation plan is owned separately in `ANDROID_MOBILE_UI_PLAN.md`. This document records review requirements and evidence rather than claiming every Android device has been tested.

## Baseline findings

The prior activity uses a vertically scrolling page but has fixed-height native text inputs, several non-wrapping button rows, paired coordinates at every width, and no explicit safe-drawing/IME inset policy. Vertical scrolling alone does not prevent horizontal clipping, text truncation at large font scales, or keyboard/system-bar overlap. Stop and pairing approval are far below the first viewport. The asynchronous preview can return after edited inputs or a Stop and restore a stale local prepared ID.

## Required review boundaries

* Measure the current window rather than classifying the physical phone. Keep content scrollable with a bounded centered tablet width. Narrow windows and large fonts need stacked fields or wrapping controls; button/card heights must grow with text. Do not clamp the user's font scale to hide overflow. Critical Stop must remain reachable in short landscape and keyboard-visible configurations.
* Handle status/navigation/cutout and keyboard insets explicitly, with resize behavior and consistent inset consumption. Check focused native input visibility instead of assuming Compose text-field behavior applies to an `AndroidView`.
* Preserve `FLAG_SECURE`, disabled Android view saving/autofill/content capture, no personalized keyboard learning, volatile Compose state, cleared saved-state bundles, disabled backup, and no activity logs or persistence. Do not disable screenshot protection to obtain test images.
* Keep all location-provider mutations behind explicit foreground Start, preserve Stop/domain revocation before asynchronous Android service callbacks, and retain phone-side pairing approval/rejection. Desktop readiness must not automatically start mock location injection.
* Keep canonical engine speed in m/s, with mph/km/h conversion only at presentation boundaries. Changing display units preserves physical speed; actual speed edits invalidate an existing local preview. Stop discards journey inputs and pending async results. Do not log numeric input errors or pairing secrets.
* Capture preview input generation and expected coordinator revision before launching background preparation. A late result cannot revive a prepared plan after edits or Stop. Do not turn coroutine cancellation into a new user-visible failure.

## Minimal meaningful qualification

Compose's test-only `DeviceConfigurationOverride` supports local forced size, font scale, and layout direction. An isolated presentation screen with synthetic inputs and inert callbacks can be rendered on one emulator at 320×480, 360×800, 640×360, 840×640, and 1280×800 dp with font scales 1.0, 1.5, and 2.0. Fixed semantic identifiers let tests assert that controls fit their parent bounds and are scroll-reachable without screenshots or real device activity. Native input bounds/accessibility can be tested with Espresso. Add a real Activity/IME inset check because an isolated forced-size Compose test alone does not prove system keyboard behavior.

Pure host JVM tests for sizing and speed conversion complement rendered checks but cannot establish that pixels or labels are unclipped. Build/lint success is compilation evidence. Report the actual configurations that ran, emulator/hardware availability, and any pending IME/rotation/font-scale cases. Do not describe a designed responsive layout as verified on all devices or screen ratios.

Sources: [Compose insets and consumption](https://developer.android.com/develop/ui/compose/system/insets-ui), [adaptive display-size guidance](https://developer.android.com/develop/ui/compose/layouts/adaptive/support-different-display-sizes), [Compose configuration overrides and isolated tests](https://developer.android.com/develop/ui/compose/testing/common-patterns), [Compose testing APIs](https://developer.android.com/develop/ui/compose/testing/apis), and [Windows emulator acceleration](https://developer.android.com/studio/run/emulator-acceleration).

## Final source findings

Reviewed `MainActivity.kt`, `MobileUi.kt`, `MobilePresentation.kt`, `MobileSessionState.kt`, and their fixture/controller/privacy tests. Presentation is stateless with inert-capable event callbacks; it has no direct provider, service, pairing, or radio authority. The activity retains explicit foreground Start, synchronous Stop revocation, and separate pairing approval/rejection.

The replacement measures the actual insets-reduced window, caps tablet content at 840 dp before evaluating font scale, stacks narrow coordinate fields, wraps buttons and mode controls, and substitutes a compact section selector in short windows. Optional Start/Pause actions can move into the scrolling status section while Stop stays in the footer. `enableEdgeToEdge`, `adjustResize`, safe drawing, and IME padding form an explicit inset policy. Native inputs now have persistent external labels and intrinsic height with a minimum; programmatic text rendering suppresses edit callbacks, so unit switching cannot invalidate or change the canonical speed accidentally.

The activity keeps `FLAG_SECURE`, excludes the complete window from autofill and content capture, clears saved-state bundles, and preserves backup restrictions. Android 10/API 29 uses the activity-level `ContentCaptureManager.setContentCaptureEnabled(false)` before any content is created; the per-view capture setter/constants are available only from API 30 and are guarded accordingly on both the decor and native inputs. The secure-window and autofill protections are unconditional. Native text fields additionally disable Android view saving, suggestions where appropriate, and personalized keyboard learning. Drafts and preferences survive configuration changes only through a RAM-only ViewModel; no saved-state adapter or persistent profile was introduced. Pairing display groups are formatting only, and the phone now explicitly instructs entering all 32 hexadecimal characters without spaces or line breaks, matching the existing Windows parser. Sources: [activity content-capture opt-out](https://developer.android.com/reference/android/view/contentcapture/ContentCaptureManager#setContentCaptureEnabled(boolean)) and [per-view content-capture importance](https://developer.android.com/reference/android/view/View#setImportantForContentCapture(int)).

Review identified two preparation races and coordinated fixes. Input generation plus a coordinator revision captured before dispatch rejects late results after edits or Stop. A separate monotonically increasing operation owner prevents an older cancelled preparation's `finally` block from clearing the busy flag of a newer operation. Controller regression tests cover both transitions. Cancellation is rethrown instead of becoming a misleading new failure message.

The declared rendered test matrix uses actual Compose measurement at 320×480, 360×800, 640×360, and 840×640 dp with font scales 1.0, 1.5, 2.0, and 2.5 on Robolectric API 35; it includes a separate API 36 compact large-font case. Tests assert root size, horizontal control bounds, Stop height/visibility, useful nonoverlapping scroll area, reachable pairing/inputs/recovery controls, measured coordinate reflow, and pairing-secret text overflow. Synthetic fixture callbacks do not start services, inject locations, approve a real computer, or change radios. Android 35/36 privacy activity tests inspect secure flags and saved-state behavior. These are meaningful rendered host checks, but they do not reproduce a real OEM keyboard, display cutout, device rotation, or every tablet size. Record executed results in build/validation documents; do not infer execution merely from the tests' presence.

The final root-reported full Android run passed **53 app tests plus 37 domain tests**, with no failures/errors/skips. It includes nine framing tests, ten rendered-layout checks, and five real-activity privacy checks, with API 29/35/36 and a 1280×800 centered-width case. These are measured host layouts; no successful PNG export or visual pixel review is claimed. No remaining source blocker was identified. Real IME focus visibility, rotation/resizing, manufacturer behavior, and any additional extreme dimensions remain explicit qualification boundaries.
