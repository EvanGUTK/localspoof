# Place categories and map legend

The user authorized category filters and a compact map legend on Windows and Android. Implementation is already authorized; this document defines the agreed contract and review checks, with no additional approval gate. Maps remain local app interfaces using existing online providers, with no account, hosted application server or added dependency. Saved places remain an explicit local action; searching does not create history or a bookmark.

Tapping a category explicitly queries Photon around the current map center only when zoom is at least 9. **Search this area** explicitly refreshes that category after the user moves the map. Moving the map alone never sends another POI request. Radius is 10 km and result limit is eight. Desktop and phone use the same category IDs and principal OSM tags:

| Category | Visible label | Accepted principal tags |
| --- | --- | --- |
| `HOTEL` | Hotels | `tourism=hotel`, `motel`, `hostel`, `guest_house` |
| `FOOD` | Food | `amenity=restaurant`, `fast_food` |
| `COFFEE` | Coffee | `amenity=cafe` |
| `SHOPS` | Shops | `shop` with a nonempty value, excluding `vacant`, `no`, `disused`, `abandoned` |
| `FUEL` | Fuel | `amenity=fuel` |
| `HEALTH` | Health | `amenity=hospital`, `pharmacy` |
| `ATTRACTIONS` | Attractions | `tourism=attraction`, `museum` |

The compact row shows Hotels, Food, Coffee and Shops, with other choices under More. Desktop has a collapsible legend; the phone has a dismissible map-key dialog explaining the live phone dot, chosen destination, road/flight lines and numbered place pins. Result rows show their matching number, name and distance from the searched map center. Distances respect the app's units. A selected result changes only the chosen draft role (origin, destination, or route stop); it cannot start playback, approve a controller, alter a live plan, or enable radio changes. Selecting and saving remain distinct actions.

Native requests target only `https://photon.komoot.io/reverse` with validated center coordinates, radius `10`, limit `8`, and constant category tag filters. No caller-supplied URL, host, endpoint, OSM filter syntax or arbitrary radius is accepted. [Photon's official API documentation](https://github.com/komoot/photon/blob/master/docs/api-v1.md) documents reverse radius in kilometers, bounded result limits and principal OSM tag filtering. Its current documentation still supports `osm_tag` while recommending installation-dependent include/exclude categories instead. Principal-tag coverage depends on the imported dataset. The UI must describe these as available provider results, not a complete inventory of businesses. No prices, opening hours, live availability or reviews are inferred from a category match.

Responses are untrusted. Accept only finite in-range Point coordinates, the selected category's exact principal tag, nonblank names at most 300 UTF-16 code units with control characters rejected, and distance no more than 10,000 meters from the request center. Tag keys are 1–40 UTF-16 code units and values 1–80, also rejecting controls. Response bodies remain bounded at 256 KiB and lists at eight; construct the narrow result shape rather than returning arbitrary provider properties. Reject invalid geometry, unknown categories, malformed tags and oversized responses. Preserve existing rate limits, active-request admission, deadlines, HTTPS certificate checks, redirect refusal, cache/cookie restrictions and privacy disclosures. Online providers receive map-center/category requests and may retain them; app-local storage does not prevent provider logging.

Android viewport messages are display metadata only, using the exact existing synthetic origin and `/viewport?lat=…&lon=…&zoom=…`. Require exactly one of each parameter, no extra query keys, user info, port, fragment or alternate origin, finite geographic coordinates, and zoom 0–24. This navigation callback is not a JavaScript interface or a new session command. It must not accept coordinates from an arbitrary web page or invoke playback mutations. The existing WebView asset allowlist, blocked default network access, CSP, storage restrictions, secure screen and disabled production debugging remain.

Request ownership captures category, map center, selected role and cancellation generation. A late result cannot repopulate another category/role, a moved search area, a cleared panel or a released view. Completed results can remain visible after panning, with a message identifying the searched area and an explicit refresh action. Clear, Stop, offline mode or disabled provider cancels/invalidate results and numbered pins. A request already in native HTTP can finish within existing limits, but its stale result is discarded. Place results and viewport state stay in RAM until explicitly saved through the existing bookmark flow.

Acceptance checks are meaningful regressions: exact category parity across native/desktop/phone; forged or mismatched tags rejected; distant/malformed coordinates and unsafe names rejected; world/low-zoom search disabled; one explicit search sends one bounded request; empty/error/loading states remain usable; cancellation and role/category/area changes discard late replies; Stop/offline/provider-disabled clear markers; numbered pins/list and legend remain accessible at compact/large-font sizes; picking a place edits a draft only. Validate fixed-host URLs and queue/rate limits without querying private phone locations. Public map examples may be used for rendering QA. Final hardware/build evidence belongs in the release validation record; source tests do not establish exhaustive worldwide POI coverage.

Implementation ownership: desktop UI agent owns renderer/category controls; mobile agent owns phone network/UI/viewport changes; root owns Windows native endpoint validation, integration, packaging and device QA; the independent reviewer owns this plan and source review record. No domain, authenticated controller protocol or live-location authority change is required.

## Phone map density correction

The user reported that phone controls left only about 15% of the map visible and authorized a less crowded layout. Keep the map as the default surface: collapse retained nearby results to an explicit results action, open the full list in a dismissible dialog, move the key to a dialog, and keep compact search/category and journey controls over the map. Desktop features and the provider/controller contracts above remain frozen.

Acceptance measures the map actually uncovered by native overlays, using measured overlay bounds rather than the full WebView dimensions. At normal 384×628 portrait content size, at least 50% must remain uncovered, with a 60% target. Check idle, ready-to-start and active journeys, category controls and retained-result states. Large-font, short-landscape and keyboard layouts may use scrolling or dialogs but must not clip controls or make Stop unreachable.

Dialogs must support Close, back and dismissal without changing the journey. Since a modal blocks underlying controls, keep immediate Stop-and-discard available in dialog chrome, outside the scrolling result/key content. Preview, local Start and approved-plan Start remain explicit user actions; connection approval and manual radio/restoration prompts stay reachable through journey/connection details. Opening, resizing, dismissing or restoring a display panel cannot start playback, approve a controller or send a provider request. Results remain in RAM and pin selection remains draft-only.
