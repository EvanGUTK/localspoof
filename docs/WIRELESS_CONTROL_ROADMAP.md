# Future wireless control

Status: architecture roadmap only. Current LocalSpoof builds require verified physical USB and deliberately reject network ADB transports. No wireless implementation, network discovery, SDK setting change or automatic transport switch is part of the current work.

Android 11+ supports workstation/device wireless debugging on the same Wi-Fi network, paired through Android's QR-code or pairing-code flow. The OS remembers that workstation authorization until it is forgotten/revoked. See the official [ADB Wi-Fi instructions](https://developer.android.com/tools/adb#connect-to-a-device-over-wi-fi). This uses local Android debugging authorization; an app account, root access and a cloud relay are unnecessary.

A future implementation must add an explicit **USB / Wi-Fi** transport choice and a separate narrowly bounded native adapter for Android's authenticated TLS wireless-debugging pairing and connection path. The user selects the phone's displayed local pairing/connection endpoint and approves the OS pairing. The native adapter must validate endpoint syntax, local-network scope, ports, transport identity and bounded command output; never expose arbitrary remote ADB servers, generic shell commands or unrestricted URLs through IPC. Keep the workstation ADB server loopback-only. Do not enable legacy `adb tcpip 5555`, silently relax physical-USB validation, turn on mDNS globally, restart a shared SDK daemon, or automatically switch transport on USB loss.

After the OS transport is established, retain LocalSpoof's independent comparison-number approval, channel-bound native-only credential, fixed preauthentication/frame/heartbeat limits and explicit Start/Stop. An OS-trusted workstation does not automatically become an approved LocalSpoof controller. Loss/reconnect needs a fresh app approval; it must not take over an existing approved controller. Discovery, if later added, is opt-in and its advertised identity is untrusted until authenticated transport/phone approval succeeds.

Airplane mode may interrupt Wi-Fi and the controller cannot reliably issue restoration over the lost connection. Wireless flight support therefore needs a separately tested policy: either a user-approved arrangement that keeps Wi-Fi available, or guided phone radio/restoration steps that remain usable after loss. Preserve phone-local Stop and playback safety; do not promise automatic radio recovery after wireless connectivity disappears.

LocalSpoof's coordinates, queries and app session authority remain RAM-only. Android/SDK workstation keys, paired-device/network trust and diagnostic state can persist outside the app. Explain that boundary and provide the official Android **Forget** / revoke-authorization steps; clearing LocalSpoof activity does not erase OS debugging trust. Verify hostile discovery, wrong device/endpoint, revoked trust, cross-channel replay, Wi-Fi/USB transition, airplane-mode loss, manual restoration and Stop before claiming wireless support.
