# LocalSpoof protocol v1.6

The phone is authoritative. TCP exists only on the desktop's loopback side of an authorized USB ADB tunnel. The phone listens on abstract local socket `localspoof.control.v1`, independently of the APK’s optional online map access. The desktop scopes ADB operations to a selected device and requires physical USB evidence (including independently checked Windows PnP/sole-USB evidence when devpath is unknown). No wireless sessions, discovery service, remote API, or generic shell command is exposed.

Frames are a four-byte unsigned big-endian byte length followed by strict UTF-8 JSON. The encoded frame limit is 1,048,576 bytes. Android imposes a full-frame deadline and JSON depth/token limits; malformed frames cannot disclose current activity. [schema.json](schema.json) describes the wire envelope; server/domain validation enforces mode-specific numeric and resource constraints.

## Pairing

The phone user enables desktop control from visible UI. Enabling an already enabled listener preserves the accepted connection. Minor version 2 replaces typed secrets with a comparison number and explicit phone approval. Windows native code generates a random 128-bit `clientNonce`; `PairRequest` sends only `payload:{clientNonce}`. The phone generates a random `pairingId` and returns `{pairingId,comparisonCode,pending:true}`. Both IDs are exactly 32 lowercase hexadecimal characters.

`comparisonCode` is the first four SHA-256 bytes of UTF-8 `localspoof-pair-v2:<clientNonce>:<pairingId>`, interpreted as unsigned big-endian, reduced modulo 1,000,000 and padded to six digits. Windows computes it independently and rejects an inconsistent value. The user checks that both screens show the same number and approves that particular pending ID on the phone. A stale approval callback cannot approve a replacement request. No typing or clipboard operation is involved.

`PollPair` sends `{pairingId,clientNonce}` on the exact accepted socket that owns the request. Until approved, it returns `ok:false,error:PAIRING_PENDING`; successful approval returns the random credential and lease `sessionId`. The desktop native layer retains nonce/token/session identity in memory and returns constructed renderer-safe status/comparison replies, rather than arbitrary wire data. Token authorization and authenticated cached/planning/resource responses additionally require that same internal socket channel. A different socket cannot retrieve or use the credential. No nonce or token appears in process arguments, URLs, files, or production logs.

The connection retains its fixed 120-second preauthentication limit, the entire arriving frame has one five-second deadline, and approved authority expires after six seconds without authenticated traffic. Idempotent requests, Hello, polling or redisplaying the number do not extend these limits. Reject, Stop, disconnect and expiry invalidate ownership; retry needs a fresh explicit request and phone approval. Windows closes only its own forward and revalidates the same selected physical phone. Current 0.7 desktop requires minor at least 6 and Hello flags `approvalPairing:true`, `livePhoneLocation:true`, `flightLegOptions:true`, `liveJourneyControls:true`, `routeStops:true`, `motionTelemetry:true`, `variableCruise:true`, `mappedRoadLimits:true`, `remainingJourneyEdits:true`, `timedPause:true`, `vacationFuelStops:true`, `hotelStages:true`, `vacationCorrections:true`. Minor-2 approval belongs to the built 0.4 baseline; minor-0/1 secret pairing is unsupported. Upgrade both components rather than fall back to secret entry.

Hello, capability, pairing, rejection, and malformed-command replies contain no current location, route, state, or phase. Snapshots require the active lease. One controller is bound to its connection; expired/disconnected/replaced leases cannot revive themselves. One pending request cannot be replaced by another nonce/channel. The number is a human comparison aid inside the authorized USB/ADB trust boundary, not a credential or a cryptographically authenticated key exchange. It does not protect a compromised host or actively rewritten transport. See [pairing plan/review](../docs/USB_APPROVAL_PAIRING_PLAN_REVIEW.md) for the security scope and qualification status.

## Commands and state

Authenticated envelopes include the lease sessionId, token, bounded random commandId, increasing sequence, and expectedRevision. Phone edits or state changes can advance revision. Authorized Stop has priority over stale revisions and cancels in-flight planning. The server's bounded deduplication cache handles exact repeated command envelopes; reuse with a different fingerprint is rejected.

PreparePlan accepts the plan shape in the schema. It calculates a complete candidate without replacing the active plan. It returns `payload:{preparedId,preview}`. CommitPlan accepts `{preparedId}` and atomically swaps only a still-valid candidate. A fresh idle session needs a visible phone Start; replacing an already armed active session can continue. Pause freezes route progress while keeping location hold updates. Stop releases providers and drops session activity.

The canonical preview fields are **geometry**, **distanceMeters**, **durationMs**, **originAirport**, **destinationAirport**, **geometrySimplified**, **originAirportAccessPoint**, and **destinationAirportAccessPoint**. These field names are shared by Android serialization and the desktop preview decoder. A simplified preview never replaces the full route used by the phone engine.

Airports and Places are bounded local searches. Heartbeat and Snapshot return only current state. A lease expires after six seconds without authenticated traffic. Losing the controller does not end ordinary phone playback. No replay log is retained.

## Live phone position and staged flight options

Only authenticated snapshots contain `payload.phoneLocation`, either null or `{point,source:DEVICE|SIMULATION,accuracyMeters?,ageMs}`. DEVICE is the latest valid fresh non-mock framework reading before mock-provider preparation; SIMULATION is the latest successfully submitted sample after arming. Do not substitute a prepared/READY origin or unsubmitted plan target. Age uses the phone's monotonic clock, must be within 30 seconds, and is advanced on Windows using time since receipt. No actual GPS lookup is promised while the GPS/network providers are replaced by test providers. Missing/stale/unavailable data is null, not a demo coordinate. No separate location command, public disclosure or history is introduced.

Snapshot/Heartbeat retries retain only their command fingerprint and a public acknowledgment, rather than a historical private response. An exact retry regenerates the latest authenticated view after matching session/token/channel and expiry checks; it does not advance sequence or renew the lease. Changed payload/envelope under a reused command ID is rejected. Mutating-command acknowledgment behavior remains unchanged. Missing/null session or token for any private command returns a public unauthorized error before private routing.

FLIGHT requests use `routeSource:FLIGHT_JOURNEY`, with `departureGroundMode` and `arrivalGroundMode` DRIVE|INSTANT and `flightTransitMode` TIMED|JUMP. Defaults are DRIVE/DRIVE/TIMED. `onlineFlightRoutes` keeps mandatory airport IDs; each road leg is nullable only for its corresponding INSTANT mode, and DRIVE online legs remain strict validated DRIVE geometry. Instant airport endpoints use selected catalog coordinates; DRIVE airport endpoints use actual validated road access within 5 km. Jumped/instant segments are not road routes and require no synthetic road connector.

Preview `segments` contains three ordered typed entries: role DEPARTURE/AIR/ARRIVAL, kind DRIVE/FLIGHT/INSTANT as applicable, points, durationMs, actual routeSource and optional routeProvider. Instant and jumped-flight durations are zero. DRIVE provenance is ONLINE_ROUTER or OFFLINE_GEOPACK; INSTANT is INSTANT_LOCATION; AIR is FLIGHT_JOURNEY. Preview geometry may be simplified but never replaces full playback routes. TIMED air samples use engine-side great-circle interpolation; a desktop animation does not assert phone placement.

Both instant ground placements and arrival placement retain submission acknowledgments before advancing. JUMP skips only the flight wait, preserving airplane-on observation, arrival injection acknowledgment, settling, session-owned restoration, phone overrides and Stop. No new generic native operation or privileged APK radio toggle follows from these options. See [trip planner plan](../docs/PHONE_LOCATION_TRIP_PLANNER_PLAN.md) for ownership, freshness, privacy and qualification limits.

## Static resource transfer

ImportGeoPack handles a single frame-sized `{pack}`. For larger static packs, BeginGeoPack accepts `{sizeBytes,sha256,totalChunks}` up to 16 MiB and 512 chunks. Each sequential GeoPackChunk contains `{transferId,index,data}`. CommitGeoPack `{transferId}` verifies exact UTF-8 size, SHA-256, JSON/resource limits and reference integrity before atomically installing validated resources. Transfers expire after 30 seconds and are dropped on error, disconnect, or Stop. Unicode chunking must preserve surrogate pairs and stay under frame limits.

Checksum validation is integrity checking; it does not verify publisher authenticity. No serialized user route is written to a static resource file.

## Radio control

With an explicitly committed USB-policy flight plan, an authenticated snapshot may contain `payload.radioRequest:{phaseId,enabled}`. Only the native bridge can issue the restricted shell operation after re-reading the matching current phase. It captures the initial setting, restores only its own change, rejects uncertain ownership, and does not blindly disable a setting that was originally enabled.

RadioPhaseResult is native-only, not exposed through the generic UI request command. The phone verifies its current phase and the observed actual system setting. Any failure falls back to guided phone settings. Stop may return static manual-recovery guidance. Shell support and OEM behavior still require real-device qualification.

## Live controls and ordered stops (minor 4)

`SetSpeeds` accepts a nonempty strict object with optional `walkMps` (0.1–3), `driveMps` (0.1–55), and `flightMps` (30–350). It changes speed targets and remaining-time estimates without resetting distance, elapsed time, stops, or radio ownership. Paused edits apply on resume. `JumpToNextStop` accepts an empty object and only an active travel phase; it requests placement at the next declared ground stop, departure airport, arrival airport, or final destination. Provider submission must succeed before advancing. Pause, dwell, boarding, airplane-mode observation, settling, and connectivity restoration cannot be bypassed. Both commands require current revision, increasing sequence, and the owning approved channel. Exact retries retain public acknowledgments and regenerate current authenticated status without mutation or lease renewal.

Snapshots expose `speeds`, `remainingMs`, `remainingMeters`, `nextStop:{point,label,index}|null`, and `waitingFor`. ETA excludes unknown user wait and is null while paused, awaiting provider acknowledgment, or waiting for a radio transition. The phone computes current remaining edge distances, road caps, stops and flight distance; Windows must not invent a countdown from the original preview. Arrival time is an estimate and can change as speeds or waits change.

Walking/driving `PreparePlan` accepts up to 32 ordered `stops:[{point,dwellSeconds?,label?}]`; dwell is 0–3,600 seconds per stop. Online geometry additionally supplies strictly increasing `stopPointIndices`, one per intermediate stop, with each selected geometry point within 250 m of its requested stop. Indices cannot be origin/final destination; custom paths use exact stop vertices, offline routing builds connected graph legs. Snapped provider vertices are the actual placement targets. Final destination is implicit. Preview `stops` carries label/dwell metadata without full playback indices. These plans remain RAM-only unless the user explicitly bookmarks a local saved copy.

Flight planning accepts `flightSpeedMps` (30–350), which determines the timed flight estimate and takes precedence over legacy `flightDurationSeconds`. Legacy durations remain supported only when the actual implied flight speed is between 30 and 350 m/s; invalid durations are rejected, never silently clamped. The airport policy now requires an open scheduled-service `large_airport` for automatic selection and manual overrides; regional/medium airports, including Jackson, Tennessee, are excluded. The catalog retains broader metadata but eligibility does not depend on airport-name guesses.

## Motion and driving controls (minor 5)

Motion was introduced in minor 5; the current components require minor 6 plus the capabilities described below. `SetSpeeds` and `PreparePlan` add optional `drivingSpeedMode` (`FIXED`/`VARIABLE`), `driveMinMps`, `driveMaxMps`, and `followRoadLimits`. Driving targets and range endpoints are finite 0.1–56 m/s, with minimum ≤ maximum; walking remains 0.1–3 and flight 30–350 m/s. Range limits describe cruising preferences, not mandatory speed during acceleration, braking, stops, or lower route caps. New fields are rejected for callers below minor 5. Revision, authenticated sequence, idempotency and lease limits remain unchanged.

Authenticated snapshots carry `speedControls` and `motion`. Motion reports successful provider submissions, never a target: current `speedMps` or null, `sampleAgeMs` or null, `sampleSequence`, `placementGeneration`, mapped `roadLimitMps` or null, `roadLimitSource` (`MAPPED`/`UNKNOWN`), and `health` (`LIVE`/`STALE`/`PAUSED`/`WAITING`/`IDLE`/`ERROR`). Samples older than 1,500 ms cannot supply gauge speed; moving samples retained across pause or an external gate cannot imply ongoing movement. `phoneLocation` optionally supplies submitted speed, bearing, sequence and placement generation for bounded display interpolation. Placement generation changes on a new committed plan or intentional jump, remains stable during normal ticks/speed edits/pause, and cancels interpolation even for a short jump initiated from the other controller. These fields remain absent from public unauthenticated responses.

Online `edgeSpeedLimits` is optional and aligned to geometry edges; finite mapped values use m/s and null means unknown. Generic router speeds must not populate it. Offline `speedLimitSource` is optional (`MAPPED`/`ESTIMATED`/`UNKNOWN`); missing provenance stays Unknown. Existing unverified/profile limits can still constrain offline route playback, but are never displayed as posted limits. The follow-limits setting affects vehicle ground travel, not walking or the air leg.

Phone playback consent is independent of the controller lease: disconnect/expiry revokes future desktop commands while the phone-consented journey continues. Stop/error/service ownership loss releases CPU work. Genuine scheduling gaps pause visibly without fast-forwarding missing travel. Airplane-mode prompts are guidance at actual engine gates, deduplicated in RAM, and never substitute for observed radio state. Restoration uses the original observed state, including ON when applicable.


## Remaining journey edits and Vacation (minor 6)

The phone retains approved geometry and editable choices separately from candidate previews. An ordinary desktop map click cannot replace an active journey. Authenticated snapshots expose `activePreview`, `activeChoices`, `editId`, `canUndo`, `timedPauseRemainingMs`, `stages` and `vacation`; public pairing/discovery responses disclose none of them. A remaining flight preview can contain the ordered suffix `[DEPARTURE,AIR,ARRIVAL]`, `[AIR,ARRIVAL]` or `[ARRIVAL]`. Rendering must not recreate completed flight legs.

`BeginRemainingEdit:{useUndo?:boolean}` acquires a temporary editing hold at a freshly acknowledged provider point, returning `{editId,confirmedOrigin,phase,choices,canUndo}`. `PrepareRemainingPlan:{editId,request}` plans outside the runtime lock and returns `{preparedId,preview}`. `ApplyRemainingPlan:{editId,preparedId}` atomically replaces only eligible future travel from that held point. `CancelRemainingEdit:{editId}` restores the approved playback/pause/radio intent. Revision, sequence, ownership, generation and preparation checks reject stale completion after Stop, cancel, disconnect or another mutation. Disconnect/lease expiry cancels a desktop-owned editing hold while phone-consented playback continues; it cannot cancel a phone-owned edit.

Local preliminary previews continue playback and have no mutation authority. Phone Apply obtains a fresh hold and rebuilds before applying; Windows exposes an explicit held editing workflow. No failed candidate replaces the approved plan. Undo stores one preceding choice set in RAM, rebuilds from the current confirmed position and excludes completed/in-progress stops. It never rewinds location, fuel consumption or spending. Airborne changes preserve the original departure and radio ownership and reroute only the air/arrival suffix; required radio gates remain authoritative.

`TimedPause:{durationSeconds:60|300|900}` pauses for a monotonic interval. Resume cancels the timer; canceling the timer leaves playback paused. Acquiring an edit cancels scheduled resume and the UI explains that an originally paused journey stays paused until Resume. `LeaveStop:{}` starts remaining hotel checkout from check-in/stay; it never jumps over checkout or provider/radio gates. Stop always revokes prepared/edit authority and terminates service-owned playback.

Ground stops add an optional stable `id` (1–128 letters/digits/underscore/hyphen) and `kind:PLACE|FUEL|HOTEL`. FUEL requires `{refillTargetLiters,pricePerLiter?,currency?}` and a DRIVE Vacation. HOTEL requires `{checkInSeconds,staySeconds,checkOutSeconds,nights,currency,nightlyPrice?,fees?}`; dwell must equal the sum of the three phases. Check-in/out each permit at most a day, stay at most 30 days, billed nights at most 365. Ordinary/fuel dwell remains at most an hour. Duplicate IDs, mismatched metadata and invalid limits are rejected. Stable IDs prevent exactly-once refill/cost events from replaying through an edit or Undo.

A DRIVE request may include `vacation:{tankLiters,startingFuelLiters,reserveLiters,litersPer100Km,fuelGrade,currency,fuelPricePerLiter?}`. Starting fuel is explicit, never assumed full. Internal volume is liters, consumption L/100 km, and distance meters; UI US/Imperial MPG, gallons and miles are converted at the boundary. Fuel grades are REGULAR/MIDGRADE/PREMIUM/DIESEL, currency is an ISO-format uppercase three-letter label, and there is no currency conversion. Tank/start/reserve limits, ordered route distance, actual station detours and reserve feasibility are checked by the phone. Hotel costs can exist independently of fuel; unknown price/fees stay unknown and mixed currencies are not summed.

The engine consumes fuel by simulated road distance. At a stop it requires a successful provider acknowledgment, holds at the station/hotel, completes the applicable duration, then records one refill or hotel event and continues. Active ledgers stay in RAM. `UpdateVacation` accepts a nonempty subset `{remainingFuelLiters?,litersPer100Km?,reserveLiters?}`; dry-validation of future reserve/refill feasibility occurs before atomic correction. Already consumed fuel and spending remain unchanged. No missing data triggers an automatic jump or fabricated station/specification.

Snapshots expose current fuel, consumed fuel, optional refill cash/hotel cost/consumed fuel value, currency, constant-consumption MPG, estimated remaining range and stop stage. Constant MPG is explicitly editable; these are estimates, not an invented speed-dependent vehicle curve. Explicit local saving stores only route/Vacation choices and typed stops, excluding playback ledgers, completed-stop history, credentials and edit authority. `vacationStops` is also advertised by the phone for typed-stop coverage.
